# 0.7.0 wait-flag wire-format extension — final recommendation

Synthesizes Investigations 1, 3, RT-safety research, and the
(deferred) Investigation 4 into a clear ship/don't-ship call for the
proposed lane-4 wait-flag protocol.

## Recommendation

**Ship the wait-flag protocol as 0.7.0**, but motivate the wire-
format bump on **RT-hygiene + community-alignment grounds**, not
performance. Specifically:

1. Add lane 4 (`producer_parked` flag) to the active SAB header.
2. Producer atomically sets lane 4 = 1 before `Atomics.wait(WRITE_IDX_LANE, ...)`,
   sets it back to 0 immediately after wake.
3. Consumer's `pull` / `pullLatest` paths read lane 4 before
   notifying — only fire `Atomics.notify(READ_IDX_LANE, 1)` if lane 4
   is non-zero.
4. CHANGELOG framing: "Adopt the RT-thread discipline of ringbuf.js
   and the broader Web Audio community: no `Atomics.notify` from
   `process()` on the steady-state no-waiter path."

This is a small wire-format extension (one new active lane in the
already-reserved 4-7 region) and a small public-API change (no
behavior change for consumers that don't park; opt-in for those that
do). All existing tests pass unchanged; the protocol activation is
producer-driven.

## Why this isn't a perf optimization

Investigation 1 measured the per-pull notify cost on the no-waiter
steady state across all three browser engine families:

| Engine | pull (notify) | pull (noNotify) | delta median |
|---|---|---|---|
| Chromium 148 / V8 (desktop) | 1.96 μs | 1.92 μs | **40 ns** |
| Firefox 151 / SpiderMonkey | 2.02 μs | 2.00 μs | **20 ns** |
| Safari 26.5 / JSC (iPhone) | 880 ns | 860 ns | **20 ns** |
| Node 22 / V8 (Bridge.bench.ts) | 1.30 μs | 1.20 μs | **~100 ns** |

All three engines short-circuit `Atomics.notify` with zero waiters
in user space (V8/JSC via a per-WaiterList hashmap; SpiderMonkey
similarly). The RFC's "syscall on every pull" framing was wrong for
every engine. The notify cost on the common path is comparable to a
single L1 cache hit (~5 ns to ~100 ns depending on engine + host).

Investigation 3 measured what the proposed wait-flag protocol's
consumer-side check costs versus the notify it eliminates:

| Run | notify Δ | protocol overhead | protocol savings | protocol NET |
|---|---|---|---|---|
| V8 Chrome run 1 | 20 ns | 65 ns | -45 ns | **-110 ns** |
| V8 Chrome run 2 | 165 ns | 55 ns | 110 ns | **+55 ns** |

The two runs **flipped the sign of the protocol's net effect**. The
protocol overhead (Atomics.load lane 4 + branch) is stable at ~60 ns
across runs. The notify cost it eliminates varies bench-to-bench in
the 20-165 ns range. On V8, **the per-pull signal is below the
bench-to-bench variance** — we can't distinguish "protocol helps"
from "protocol hurts" from "protocol does nothing" at single-run
precision.

The honest perf reading: **on V8, the wait-flag protocol's per-pull
impact is statistically indistinguishable from zero**. Even if a
tighter measurement (10× sample size or 10-run median) eventually
resolved the sign, the magnitude is on the order of single-digit
percent of one cache hit per pull. At 375 Hz audio-thread cadence
that's 5-40 μs of CPU per second — 0.0005-0.004% of one core.
**This is not a perf optimization.** Investigation 4's AudioWorklet
jitter measurement (deferred) would confirm the obvious: a per-pull
cost difference 1000× below the audio quantum budget cannot affect
jitter.

## Why ship anyway — the RT-hygiene case

The spec / implementation reality:

- **W3C Web Audio API**: silent on `Atomics.notify` from `process()`.
- **ECMAScript TC39**: explicitly permits `notify` from any agent,
  including the `[[CanBlock]] = false` AudioWorklet global scope.
  The `EnterCriticalSection` step on `notify` is per-WaiterList, not
  global — uncontended notify never acquires a lock.
- **All three engines** (V8, SpiderMonkey, JSC) implement the
  permissive standard behavior. No console warnings, no throttling,
  no observable degradation when calling notify from `process()`.

So from a spec-compliance standpoint, the protocol is unnecessary —
the library could keep calling notify from `process()` indefinitely.

**But the practitioner consensus disagrees.** From Paul Adenot —
Web Audio spec editor + author of ringbuf.js, the reference SPSC
ring for Web Audio:

> "`wait` is not available in the AudioWorkletGlobalScope, and
> `notify` is most probably unsafe to use from a real-time thread
> cross-platform, since it takes a lock on at least some platforms."

The "lock" is the per-WaiterList `EnterCriticalSection` mutex. On
the *uncontended* notify path (which Investigation 1 measured), the
lock is never acquired. On the *contended* path (a parked waiter
exists on the same WaiterList), the notify call DOES acquire the
mutex to inspect and modify the wait list. This is a real
priority-inversion risk on the audio thread — small, rare, but
present and unbounded in theory.

Every credible reference implementation respects this hygiene
boundary:

- **ringbuf.js** — zero `Atomics.notify` calls anywhere; only
  `load` / `store`.
- **Loke.dev's zero-jitter ring** — same, only `load` / `store`.
- **Chrome's Audio Worklet design-pattern guide** — uses notify
  only on the Worker side, never inside `process()`.

`webgpu-audio-bridge` is currently the outlier: it calls
`Atomics.notify` unconditionally from `pull` / `pullLatest`, which
the AudioWorklet calls from `process()`. The proposed wait-flag
protocol moves the library into the consensus: the audio thread
**only** notifies when it has cryptographic evidence (lane 4 = 1)
that a producer is parked and needs to be woken. On the steady
state, the consumer never even attempts to enter the critical
section.

### The contended-path cost we didn't measure

When `Atomics.notify` actually wakes a parked waiter, it goes to the
kernel (`futex_wake` on Linux, `NtReleaseKeyedEvent` on Windows,
`__ulock_wake` on macOS). Typical cost: 1-10 μs round-trip on the
caller's side, with cache coherence + scheduler latency on top. At
375 Hz pull cadence, even one contended notify per second adds
detectable jitter if it falls in a vulnerable quantum.

The wait-flag protocol doesn't *avoid* this cost when a real wake
needs to happen — the protocol fires the same notify in that case.
What it does is **eliminate the audio thread's ability to racingly
enter the critical section at all**. The only path to the lock is
through the lane-4 gate. If the producer never parks, the audio
thread never even attempts the critical section. If the producer
DOES park, the audio thread takes the lock to wake it — which is
exactly the case where the lock cost is justified.

Without the protocol, every pull is a *potential* contended-notify.
With the protocol, every pull is *deterministically* either an
uncontended fast-path skip (lane 4 = 0) or a justified wake (lane
4 = 1).

### Alignment value

A library reviewer auditing the audio-thread code asks: "does your
worklet call `Atomics.notify`?" The current answer is "yes,
unconditionally." That immediately reads as suspicious to anyone
who's read Adenot's blog post or ringbuf.js source. The protocol
turns the answer into "only via a one-instruction lane-4 check —
the audio thread never racingly enters the wait-list critical
section." That's the answer that aligns with the established
norms.

## Cost of shipping the protocol

| Item | Cost |
|---|---|
| One new active SAB lane (lane 4, currently reserved) | Already accounted for in the header layout. |
| Producer-side bookkeeping: 2 `Atomics.store` per park/wake cycle | Trivial — only on the rare parking path, not on hot push/pull. |
| Consumer-side check: 1 `Atomics.load` + branch per pull | ~55-65 ns per pull (measured). Below the bench-to-bench variance of the notify cost it replaces. |
| Wire-format break | Producer + consumer must both speak the protocol. Default-on for `Bridge<S>` and the facades; opt-out for callers who want pre-0.7 wire behavior. |
| Documentation surface | README + CHANGELOG updates; one new section explaining the protocol + the RT-hygiene rationale + citation of Adenot's blog post. |
| Test surface | One new pin: the protocol round-trips correctly through a real produce/consume cycle, including the case where the producer parks + the consumer wakes it via the wait-flag-gated notify. |

The wire-format-break implication is that 0.6.x peers and 0.7.x
peers can no longer share a SAB if the 0.7.x peer is the producer
(it would set lane 4 = 1 expecting wake-up gating; a 0.6.x consumer
would never check lane 4 and notify always). That's the canonical
"wire-format change → minor bump" trigger from CLAUDE.md.

## Scope guidance for the 0.7.0 cohort

Per CLAUDE.md's "Extended slowdown from 0.7.0 onward" clause, the
0.7.0 promotion is the **first** patch of a deep cohort that should
go to 0.7.99 or beyond before any 0.8.0 is considered. The wait-flag
protocol is exactly the right shape for `0.7.0 itself`:

- One coherent wire-format change (lane 4 activation).
- One coherent public-API addition (producer-side opt-in to parking
  semantics; consumer-side automatic gating).
- One coherent RT-hygiene story for the CHANGELOG entry.

Subsequent 0.7.x patches can then accumulate:

- 0.7.1 — additional documentation (the wait-flag protocol's
  cross-engine perf data, Adenot citation, the four investigations'
  evidence summary).
- 0.7.2 — contended-notify benchmark cell (Investigation 4-lite) that
  measures the actual kernel-wake cost when the protocol's notify
  fires. Useful for sanity-checking the protocol works as designed
  in the rare-but-real wake case.
- 0.7.3+ — whatever else surfaces in the meantime.

## Open items before 0.7.0 ships

The recommendation above is "ship." These would refine but not change
the call:

1. **Firefox + Safari Investigation 3 runs.** The Investigation 1
   Firefox + Safari data predates the wait-flag shim. Re-running on
   the updated browser harness (still live on
   `http://localhost:5175/`) would confirm whether the V8 noisy-zero
   result reproduces on other engines or whether one of them shows a
   consistent positive signal worth highlighting in the CHANGELOG.
   *Not blocking* — the RT-hygiene case stands regardless.

2. **Tighter V8 measurement (multi-run median).** A 10×10 batch run
   on V8 would tighten the protocol-net measurement from ±100 ns to
   ±10 ns, possibly resolving whether the protocol is genuinely
   net-positive or net-negative or net-zero on V8. *Not blocking*
   — the magnitude is small enough that the sign doesn't change
   the ship decision.

3. **Investigation 4 (real AudioWorklet jitter).** Building a
   realistic AudioWorklet harness with notify-toggle + load-induced
   jitter measurement would confirm the obvious: a per-pull cost
   difference 1000× below the audio quantum budget cannot affect
   jitter. *Skippable* — Investigations 1 + 3 + spec research are
   sufficient for the planning call. The harness investment makes
   sense if there's a future RT-safety question that needs the same
   infrastructure.

4. **Contended-notify cell.** Measure the actual cost of
   `Atomics.notify` when there IS a parked waiter — the kernel-wake
   case the protocol can't avoid. This is informational, not
   protocol-deciding: shipping the protocol doesn't change the
   contended-path cost, only its frequency. *Skippable until the
   0.7.x patch series picks it up* (proposed for 0.7.2).
