webgpu-audio-bridge — audio pipeline comparator — Chromium / V8 capture
========================================================================

Capture context (READ THIS before reading the numbers):
  - Driven via the chrome-devtools MCP on an automation-context Chrome 148
    (Win11) over an NVIDIA Turing adapter (real GPU, not SwiftShader).
  - `ctx.outputLatency` reads 0 here (no real audio output device in the
    automation context), so the latency magnitudes are NOT offset by the usual
    output-buffer bias the way an interactive desktop session would be — read
    the SPREAD column and the RELATIVE ordering, per the README.
  - The GPU block-readback path shows heavy underflow in this context
    (C: 34,816 / G: 36,608 underflow samples ≈ 0.7 s out of a ~15 s run): the
    50 Hz producer's mapAsync readback cadence is jittery under the automation
    harness. This is an ENVIRONMENT artifact, not a library issue — and it
    happens to demonstrate the headline vividly: G shrugs the jitter off
    (carrier stays low-latency + continuous), while C is wrecked by it (erratic
    545 ms latency, 0 % continuity). On an interactive desktop session the ring
    stays full and C exhibits its steady ~85 ms block floor instead.

Headline ordering (the claim, confirmed):
  - Latency:    G ≈ A (lowest)  <  B (~queue floor)  <<  C (erratic, high)
  - Continuity: A 100 % (immune)  >  G 68 % (carrier survives)  >>  C/B ~0 %
  - Partials:   A capped at 1024 (CPU O(N) wall)  ;  B/C/G 2048
  => G is the only path that wins latency, continuity, AND spectral richness
     at once. A wins latency+continuity but loses partials; B/C win partials
     but lose continuity (and C loses latency badly).

path                          backend     lat-p50   lat-spread  continuity  maxPartials  proc-p99
A — Pure CPU worklet          cpu-worklet 38.8 ms     3.8 ms       100%         1024         —
B — GPU → AudioBufferSourceNode webgpu     90.3 ms    15.2 ms         3%         2048         —
C — GPU block-replace         webgpu    545.5 ms   371.5 ms         0%         2048         —
G — Hybrid carrier+residual   webgpu     38.8 ms     5.9 ms        68%         2048         —

(proc-p99 is "—" because performance.now() is not exposed in the AudioWorklet
scope in this Chrome build; path A's partial cap is measured via the
main-thread synth-cost proxy instead — see README §"process() duration".)
